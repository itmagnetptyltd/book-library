## Is the Book ID entered by the person adding the Book, or issued by the application?

The application should issue the Book ID automatically. The Add Book form should not ask the user to enter a Book ID.

## Must every Book ID be different, and what should happen when one already in use is submitted?

Every Book ID should be unique. Since the application generates the Book ID, duplicate Book IDs should not normally occur.

## May the Book ID of a deleted Book be given to a Book added later?

A deleted Book's ID should not be reused. Each newly added Book should receive a new unique Book ID.

## What currency is Price in, and how many decimal places does it carry?

Use one fixed currency for the application, with Price stored as a numeric value and displayed with two decimal places. The exact currency is not specified in the brief, so this should be confirmed with the client.

## Is Language free text, or chosen from a fixed list?

Language can be entered as simple text. No fixed language list is specified in the brief.

## Which of a Book's five fields may be left empty when it is added?

All Book details should be entered when adding a Book. Book ID is generated by the application, so the user is responsible for providing Name, Author, Language, and Price.

## What should the person see when adding a Book fails?

The user should see a clear validation/error message in the Add Book popup, and the entered values should remain available so they can correct the problem and submit again.

## Does deleting a Book destroy it, or keep it and hide it?

Deleting a Book should remove it from the library. A deleted Book does not need to be displayed in the gallery.

## Should the application ask the person to confirm before a Book is deleted?

Yes. The application should show a simple confirmation before permanently deleting a Book.

## What is "a simple data store", and where does it keep the Library?

Use a simple SQLite database stored locally with the application. This keeps the Book Library persistent while remaining easy to run on a local development PC.

## Must Books still be in the Library after the application is stopped and started again?

Yes. Books should remain in the Library after the application is stopped and started again.

## Are "users" one kind of person or several, and must anyone sign in before adding or deleting a Book?

No authentication or multiple user roles are required. Anyone using the local application can view, add, and delete Books.

## If the Home page is open in two browser tabs, must each tab show what the other has added or deleted?

No live synchronization between browser tabs is required. The tab performing the operation should update immediately; another tab can reflect the change after it is refreshed.

## In what order should Book cards appear in the Gallery?

Books should appear with the newest added Books first, so a newly added Book is immediately visible in the gallery.

## What should the Home page show when the Library holds no Books?

The Home page should show a simple message indicating that there are no Books yet and invite the user to add the first Book.

## Does "immediately displayed in the gallery" rule out reloading the Home page?

The Book should appear immediately after a successful submission. A full page reload is acceptable as long as the newly added Book is displayed immediately after the operation completes.

## Should the Add Book form close itself after a Book is added?

Yes. After a successful Book is added, the popup should close and the new Book should appear in the gallery.

## Is the "Delete option" on the Book card the same control as the "Delete button", or two separate things?

They refer to the same Delete control. Each Book card should have one Delete button/option.

## Must the Gallery show every Book on one page, however many there are?

Yes, for the simple local application, all Books should be displayed in the gallery. No pagination is required unless the number of Books becomes impractical.

## What screen sizes must the application be usable at?

The application should be responsive and work well on the local development PC desktop browser. Basic support for smaller screen sizes should be provided where practical.

## What would make the interface "clean and attractive" enough for the client to accept it?

A simple, modern, clean, and user-friendly interface with a responsive gallery/grid layout, clear Book cards, an obvious "+ Add Book" button, and simple Delete controls should be sufficient. No specific branding or design system is specified.

## Is "avoid unnecessary dependencies" a preference, or a rule a reviewer may enforce?

Avoid unnecessary dependencies. Use only the packages that are genuinely needed to implement the application, keeping the project simple and easy to run locally.

## Can a Book be changed after it has been added?

Editing is not required by the brief. The application only needs Add and Delete functionality. If a Book was entered incorrectly, it can be deleted and added again.

## Which Node.js version, operating system and browser must the application work on?

The application should run on the local development PC using a currently supported Node.js version and a modern desktop browser. The exact Node.js version, operating system, and browser are not specified in the brief and should ideally be confirmed before delivery.

## Will the application ever be reachable from outside the local development PC?

No. The application is intended to run locally on the development PC and does not need to be deployed as a public or externally accessible application.

## What currency is Price in, and how many decimal places does it carry?

All prices are in one currency: BDT (Bangladeshi Taka). Price should always be displayed with two decimal places.

## What screen sizes must the application be usable at?

The application only needs to be usable on a desktop browser on the local development PC. Phones and tablets are not in scope.

## What would make the interface "clean and attractive" enough for the client to accept it?

A plain, tidy, modern and user-friendly layout is acceptable. There is no specific brand, colour scheme, reference site, or font that needs to be followed.

## Which Node.js version, operating system and browser must the application work on?

The application should work on the local development PC using a currently supported Node.js version and a modern desktop browser. No specific operating system or browser version is required beyond the local development environment.
