# Plan — REQ-BOOK-012@v1

**The Library is held in a data store outside the page that displays it.**

Status `agreed`, version 1, no dependencies. This is the first slice of the
project: `src/` currently holds only `.gitkeep`, and REQ-BOOK-001, REQ-BOOK-007
and REQ-BOOK-009 all depend on this one.

Planned 2026-08-21 against `.brain/requirements/book.yaml` as clarified by the
client answers of the same date.

---

## What must be true

The five acceptance criteria, restated as behaviour to build:

1. **The page does not hold the Library.** A Book added, then the Home page
   closed and opened again, is still returned for the Gallery. Nothing depends on
   a page staying open.
2. **The Library survives the process.** A Book added, then the application
   stopped and started again, is still returned for the Gallery.
3. **The store is a SQLite database file.** After a Book is added, that Book is
   present in a SQLite file held with the application on the local development
   PC — readable by opening the file, not only through the running application.
4. **The store is local.** The Library is held on the local development PC, not
   in an external or hosted service.
5. **Stored Books are not editable.** No operation is offered that changes an
   existing Book's stored details. The store's public interface has no update.

Criteria 1 and 2 overlap in what they exclude, but they are not the same test:
1 rules out in-page state, 2 rules out in-process state. Both get a test.

---

## Approach

A single module owns the Library and is the only place SQL exists. Everything
above it — the HTTP layer in REQ-BOOK-011, the Gallery in REQ-BOOK-001 — talks
to that module's functions and never to the database.

The store exposes exactly three operations, and deliberately no fourth:
`listBooks()`, `addBook()`, `deleteBook()`. Criterion 5 is satisfied by the
absence of an update, and that absence is asserted by a test so it cannot be
added later without something going red.

Plain JavaScript, ESM, no build step, `node:test` as the test runner. That keeps
the production dependency count at whatever SQLite costs and nothing more, which
is what REQ-BOOK-013 asks for.

**Files to create:**

| File | Holds |
|---|---|
| `src/library/library-store.js` | `listBooks`, `addBook`, `deleteBook`. The only module containing SQL |
| `src/library/schema.sql` | The `books` table definition, applied on first open |
| `src/library/database.js` | Opens the SQLite file, applies the schema if absent, returns the handle |
| `src/config.js` | Resolves the database file path. One place, read once |
| `tests/library/library-store.test.js` | The tests below |
| `package.json` | Type module, `test` script, dependency declarations |
| `.gitignore` | Add the database file — data is not source |

`package.json` at the repository root is required, not a layout choice: no
language adapter currently matches this project, so gate G3 scans zero test
files and reports coverage it cannot see. Creating it is what turns the gates on.

**Ordering.** `config.js` → `schema.sql` → `database.js` → `library-store.js` →
tests last is the wrong order. Tests first, per `/tdd`: the skeleton below is
written and failing before any of those files exist.

## Test skeleton

`tests/library/library-store.test.js`. One test per acceptance criterion,
each pinned to the requirement at its current version. Names state the
behaviour, not the function.

```js
// @covers REQ-BOOK-012@v1
test('a Book added through one store handle is returned by a later one', ...)
//   Arrange: open a store over a fresh temp database file; addBook(aBook())
//   Act:     close it; open a second store over the same file
//   Assert:  listBooks() returns a Book carrying those details
//   Falsifies: the Library living in page or module state

// @covers REQ-BOOK-012@v1
test('a Book survives the application being stopped and started again', ...)
//   Arrange: add a Book, then dispose of every handle and module reference
//   Act:     re-import the store fresh and open the same file
//   Assert:  listBooks() still returns that Book
//   Falsifies: the Library living in process memory

// @covers REQ-BOOK-012@v1
test('an added Book is present in the SQLite file on disk', ...)
//   Arrange: add a Book through the store
//   Act:     open the database file directly, outside the store module
//   Assert:  a row for that Book is present in the books table
//   Falsifies: a JSON file, an in-memory database, or any non-SQLite store

// @covers REQ-BOOK-012@v1
test('the Library is held in a file on the local machine, not a remote service', ...)
//   Act:     read the resolved database location from config
//   Assert:  it is an absolute filesystem path inside the project directory,
//            and carries no URL scheme, host or port
//   Falsifies: a hosted or networked store

// @covers REQ-BOOK-012@v1
test('the store offers no operation that changes a stored Book', ...)
//   Act:     inspect the store module's exports
//   Assert:  exactly listBooks, addBook and deleteBook — no update, edit,
//            patch or save
//   Falsifies: an editable Library

// @covers REQ-BOOK-012@v1
test('a deleted Book is no longer returned by the store', ...)
//   Supporting test. Not its own criterion here — deletion belongs to
//   REQ-BOOK-009 — but the store cannot be built without it, and REQ-BOOK-009
//   will annotate its own behaviour separately.
```

Each test builds its own database in a fresh temporary directory and removes it
in `t.after()`. No shared state, no shared file, so the suite passes in parallel
and in any order.

## Decisions this forces

Four, and the first three want an ADR before code rather than after.

**1. Which SQLite binding — and this is the one to settle first.**

I told you earlier that "currently supported" Node includes 20, which has no
built-in SQLite, so a third-party driver was forced. **That was wrong and it
changes the answer.** Node 20 reached end of life in April 2026 — four months
before today's date — so the currently-supported range REQ-BOOK-011 refers to is
Node 22 and above, and every version in it ships `node:sqlite`. SQLite can cost
**zero** production dependencies, which is the outcome REQ-BOOK-013 most wants.

The catch is real though: **this machine runs Node v20.17.0**, below the range
and past EOL. Under the recommended option the project will not run here until
Node is upgraded.

- **`node:sqlite`** — built in, no dependency, no native build. Needs Node ≥ 22.5,
  and on 22.x it is behind `--experimental-sqlite`; the flag requirement was
  dropped in a later major. **I have not verified the exact version at which the
  flag stops being needed, and the plan should not be approved on my say-so** —
  it decides whether the start command carries a flag. Worth ten minutes against
  the Node docs before the ADR is written.
- **`better-sqlite3`** — one production dependency, runs on older Node, but is a
  native module needing prebuilt binaries or a build toolchain on Windows. It
  works today on this machine without upgrading Node.

**2. Plain JavaScript or TypeScript.** I have planned plain JS with `node:test`,
because the project's own `rules/javascript/testing.md` argues a project told to
avoid unnecessary dependencies cannot answer for a test runner Node already
ships. Adding `tsconfig.json` would switch the adapter, the gates and the rule
set. Worth an ADR only because it is hard to reverse later, not because it is
close.

**3. How Book ID is generated, and why the obvious choice is wrong.**
REQ-BOOK-007 requires that a deleted Book's ID is never given to a later Book. A
plain `INTEGER PRIMARY KEY` in SQLite **reuses** rowids after the highest row is
deleted, which breaks that criterion silently — delete the last Book, add
another, and it takes the dead Book's ID. `AUTOINCREMENT` exists precisely to
prevent that. This is a one-word schema decision that a test will catch and a
casual reading will not.

**4. How Price is stored.** REQ-BOOK-002 requires exactly two decimal places in
BDT. Storing a decimal price as SQLite `REAL` is floating point, and prices that
survive a round trip unchanged are not guaranteed. Storing minor units as an
`INTEGER`, or the decimal as `TEXT`, avoids it. Not an ADR, but it is a schema
choice that is expensive to change once Books exist.

## What I am unsure about

- **Criterion 4 is weakly falsifiable.** A test can assert the configured
  location is a filesystem path with no host or scheme. It cannot prove the
  application contacts no external service. The test I have proposed checks the
  strongest thing available, and that is less than the criterion literally says.
- **Criteria 1 and 2 may collapse into one test in practice.** If the store holds
  no module-level state, the same setup exercises both. I have kept them separate
  because they exclude different failures, but a reviewer may reasonably call the
  second redundant.
- **The store's interface is my choice, not the requirement's.** Three functions
  and no update is the shape criterion 5 implies, but the requirement never says
  the Library must be a module with an interface. If you want a class, or a
  repository object, this is the moment to say so — REQ-BOOK-001, -007 and -009
  will all be written against whatever this slice chooses.
- **I have not proposed where the database file lives** beyond "inside the
  project directory". `src/` is for the application; a database file is data, not
  source, and I am not confident it belongs under `src/` at all despite the rule
  that everything the application is made of goes there. Worth your call.
- **The Node version question above is unresolved** and I would rather you
  confirmed it than took my version numbers on trust.
